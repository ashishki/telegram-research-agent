# UTD Nebula: фактическая интеграция и пакет для следующего агента

Проверено 11 октября 2026. Дополнение к [общему плану](README.md). Владелец запросит API key; текущая работа — исследование и задачи, без реализации, получения ключа, подключения аккаунтов или запуска сборщиков. Это уточнение снимает общую отсрочку **проектирования Nebula**, но не отсрочку Canvas. Первый общий пакет D01–D03 сохраняется.

## Вывод

**Nebula пока не интегрирована в наш runtime.** В документах есть намерение использовать её, в тесте — условная ссылка `source_nebula_1`. Реализованные UTD watch и Canvas читают другие источники. Получение ключа само по себе не включит Nebula: нужно полноценное подключение данных к существующим Search/Academic/Brief/Watch и подтверждаемым действиям.

Предлагаемый основной путь — hosted `https://api.utdnebula.com` с `x-api-key`, выбранными GET-маршрутами и общими политиками ассистента. `api-tools` нужен разработчикам данных Nebula: он собирает, разбирает и загружает данные; штатному клиенту API его установка не требуется. Поднимать собственные Go API, MongoDB и браузерный сборщик для первого подключения не предлагается. [Инструкция API](https://github.com/UTDNebula/nebula-api/blob/66695fd768b8d5a1e4dc6a3c4df90ddd955553c0/README.md), [назначение api-tools](https://github.com/UTDNebula/api-tools/blob/5375e688724dce67dc2768dbae82e9af1ebb29e6/README.md).

## Уточнение владельца: максимально рабочее решение

Цель — полностью пригодная для ежедневного использования интеграция. Размер связующего кода не является критерием успеха. Первые endpoints и ограниченный canary ниже — промежуточные шаги; на них работа не заканчивается. D51–D55 уточнены без увеличения количества карточек и без реализации в этой сессии.

Готовые компоненты имеют приоритет при подтверждённой пригодности. На старте D51 выбрать и записать способ подключения: поддерживаемый официальный SDK, если он появится/будет предоставлен; генерация совместимого клиента по Swagger; либо существующий HTTP transport проекта с typed adapter. В двух исследованных snapshots готового Python SDK не найдено. Сравнивать покрытие реально нужных маршрутов, актуальность схем, поддержку timeout/cancel/retry и стоимость сопровождения. Собственная нормализация и связь с нашим ассистентом нужны при любом варианте. Не создавать отдельный SDK или второй HTTP framework ради архитектурной симметрии.

Завершённый результат включает:

| Область | Обязательный результат |
| --- | --- |
| Учебный контекст | Календарь выбранных семестров и sessions; поиск и сравнение курсов, секций и преподавателей; работа с syllabus и prerequisites как исходными сведениями; уточнение неоднозначных названий и продолжение разговора. Нет вывода о личном enrollment из каталога. |
| События и возможности | Поиск подходящих событий, клубов и предложений; место проведения и контекст комнаты, если данные доступны. Поддержка выбранных наборов входит в целевую интеграцию. Включение в личный Brief зависит от интересов владельца, а не от наличия endpoint. |
| Работа с найденным | Сохранить, сравнить, объяснить применимость, связать с проектом/учебной целью, открыть первоисточник, вернуться к результату и исправить личный контекст. История и source identity сохраняются после рестарта. |
| Brief и Watch | Полное покрытие выбранного окна или видимый partial; отбор до ограничения числа карточек; Localist/Nebula дубли объединяются; изменения дат/места и снятые записи обработаны. Уведомления только по выбранным темам, без повторов и ежедневной настройки. |
| Подтверждаемые действия | Из результата готовится календарный draft или напоминание с источником, датой и timezone; выполнение использует общие D28/D32. Если общий Act ещё не готов, это явно открытая часть полного сценария. |
| Надёжность | Долговечное состояние обновления по источнику/окну, возобновление после рестарта, ограниченные retry/backoff, защита от повторных уведомлений, честный stale cache, изоляция отказавшего dataset, отзыв/замена ключа, статус и остановка пользователем. |
| Эксплуатация | Понятная настройка выбранных данных, безопасная диагностика, версия проверенного API contract, runbook восстановления. Истечение доступа или schema drift дают понятное состояние и сохраняют работу остальных источников. |
| Доказанная польза | Проверка реального API, затем 14 дней работы и два недельных обзора; установленные ниже сценарии и критерии. Успешный GET, synthetic PASS или первые 20 запросов не означают готовность. |

Данные вне выбранного контекста не нужно постоянно скачивать. Пользователь должен получать полный ответ на свою задачу с честными границами охвата; фоновая активность остаётся целевой и управляемой. Бюджеты защищают от бесконтрольных циклов: при достижении лимита задача сохраняет продолжение и показывает неполноту, а не молча превращается в короткий ответ.

Если hosted API не обеспечивает нужное покрытие или надёжность, D55 должна привести к работающему решению пробела: повторно использовать подходящий компонент api-tools, официальный источник или другой допустимый способ получения данных. Не исключать готовый компонент только потому, что он на Go. Выбор требует конкретного сценария, совместимости и понятного обслуживания; доступ к чужой MongoDB и полномасштабный crawler не предполагаются автоматически.

### nebula-api

Go REST API над собранными данными. README направляет за ключом в Nebula Labs Discord с описанием сценария; заголовок — `x-api-key`. Нужен доступ к публичным данным кампуса, а не NetID/пароль студента. [README](https://github.com/UTDNebula/nebula-api/blob/66695fd768b8d5a1e4dc6a3c4df90ddd955553c0/README.md).

| Маршруты в исследованном коде | Предлагаемая польза | Ограничение |
| --- | --- | --- |

Первый пакет. | ID семестра строковый, например `26F`; `current` выбирает запись с `timeline=current`, а не вычисляет персональный семестр. Выбирать term/session явно. |

Маршруты и типы: [Swagger](https://github.com/UTDNebula/nebula-api/blob/66695fd768b8d5a1e4dc6a3c4df90ddd955553c0/rest/docs/swagger.yaml), [схемы](https://github.com/UTDNebula/nebula-api/blob/66695fd768b8d5a1e4dc6a3c4df90ddd955553c0/rest/schema/objects.go), [academic controller](https://github.com/UTDNebula/nebula-api/blob/66695fd768b8d5a1e4dc6a3c4df90ddd955553c0/rest/controllers/academic_calendars.go).

Нужные детали контракта для кодирующего агента:

- Ответы используют envelope `status`, `message`, `data`; `data` зависит от endpoint. Валидировать HTTP status и envelope, не считать любой JSON успехом. [APIResponse](https://github.com/UTDNebula/nebula-api/blob/66695fd768b8d5a1e4dc6a3c4df90ddd955553c0/rest/schema/objects.go).
- Course/section search используют `offset` и разрешённые поля. Размер страницы задаётся сервером, default в исходнике 20; поддержка произвольных `limit`, `q` и универсального next cursor не подразумевается. Продвигать offset на фактически полученное число, дедуплицировать ID, ограничивать pages; полный охват не заявлять при изменяющейся выборке. `/all` не использовать. [Pagination](https://github.com/UTDNebula/nebula-api/blob/66695fd768b8d5a1e4dc6a3c4df90ddd955553c0/rest/configs/setup.go), [default](https://github.com/UTDNebula/nebula-api/blob/66695fd768b8d5a1e4dc6a3c4df90ddd955553c0/rest/configs/env.go), [filter](https://github.com/UTDNebula/nebula-api/blob/66695fd768b8d5a1e4dc6a3c4df90ddd955553c0/rest/schema/filter.go).
- `/calendar/{date}` возвращает вложенные `buildings → rooms → events`; отсутствие документа может дать успешный ответ с пустым `buildings`. Это не доказательство отсутствия событий в университете или свежести загрузки. [Calendar controller](https://github.com/UTDNebula/nebula-api/blob/66695fd768b8d5a1e4dc6a3c4df90ddd955553c0/rest/controllers/calendar.go).
- У AcademicCalendar есть `url`, sessions и строковые даты; у события — `event_website`, у section — `syllabus_uri`. Проверять каждый URL отдельно перед fetch. Универсального `updated_at` в этих схемах не найдено: `fetched_at` не равно времени обновления upstream. [Схемы](https://github.com/UTDNebula/nebula-api/blob/66695fd768b8d5a1e4dc6a3c4df90ddd955553c0/rest/schema/objects.go).
- В annotations dev server указана quota `STANDARD:1000` в минуту на project. Это **не** подтверждённый лимит будущего ключа и не целевая частота нашего polling. Реальный лимит, 429/Retry-After и доступные datasets проверить после выдачи ключа. [Server annotations](https://github.com/UTDNebula/nebula-api/blob/66695fd768b8d5a1e4dc6a3c4df90ddd955553c0/rest/server.go).

Production Swagger UI открылся через web-инструмент без содержимого схемы. Анонимные запросы Python к `/swagger/doc.json` и `/swagger/swagger.json` получили HTTP 403; web-инструмент также не прочитал JSON. Причина 403 не установлена. Это ограничение текущего исследования, не вывод о доступности API с будущим ключом. Бизнес-endpoints с ключом не вызывались.

### api-tools

Это Go CLI: scraper → parser → uploader. Uploader подключается непосредственно к MongoDB через `MONGODB_URI`; обычный API key не заменяет этот доступ. В зависимостях есть ChromeDP, Mongo driver и Google GenAI. Импортировать CLI как runtime dependency нашего Python-бота не предлагается. [Uploader](https://github.com/UTDNebula/api-tools/blob/5375e688724dce67dc2768dbae82e9af1ebb29e6/uploader/database.go), [go.mod](https://github.com/UTDNebula/api-tools/blob/5375e688724dce67dc2768dbae82e9af1ebb29e6/go.mod).

Daily runner описывает события, weekly — academic calendars/discounts/degrees, monthly — map/budgets. Это расписание скриптов в репозитории, не доказательство, что production обновляется именно так и успешно. [Runners](https://github.com/UTDNebula/api-tools/tree/5375e688724dce67dc2768dbae82e9af1ebb29e6/runners).

Существенный факт: parser академических календарей обращается к `gemini-2.5-pro` при отсутствии cache. Следовательно, по исходнику это результат машинного извлечения, который может ошибаться даже при валидной JSON-схеме. Срочные сроки следует сверять с исходным PDF/официальной страницей. Наличие такого parser не доказывает, какой pipeline создал конкретную production-запись. [Parser](https://github.com/UTDNebula/api-tools/blob/5375e688724dce67dc2768dbae82e9af1ebb29e6/parser/academicCalendarsParser.go), [источник календарей](https://github.com/UTDNebula/api-tools/blob/5375e688724dce67dc2768dbae82e9af1ebb29e6/scrapers/academicCalendars.go).

У обоих репозиториев MIT-лицензия на код; условия использования наборов данных, кэширования и перераспространения уточняются отдельно. Самостоятельный запуск api-tools — условная D55 при измеренном пробеле hosted API, в том числе выявленном на ранней проверке. Не делать автоматический scraping fallback на 401/403/429.

## Как это будет выглядеть для владельца

1. «Что важного по UTD на следующей неделе?» — не более трёх релевантных находок, причина важности, term/session, источник и состояние актуальности. Если подходящего нет — короткий пустой результат.
2. «Сравни эти два курса для моего проекта» — описания, секции и преподаватели из выбранных записей; персональная применимость вычисляется локально. Недостающие prerequisites/enrollment не достраиваются моделью.
3. «А это относится к моему семестру?» — продолжение по предыдущей карточке, а не повторный ввод ID. Несовпадение session показывается явно.
4. «Следи за изменением этого срока» — точный preview предмета/периода наблюдения, затем общая Watch-подписка. Сообщение только об изменении или заранее выбранном напоминании.
5. «Добавь событие в календарь» — черновик существующего Act-контура; итоговая запись после подтверждения через выбранного календарного провайдера. API Nebula для этого ничего не записывает.

Новый экран/бот и обязательные команды `/nebula_*` не нужны. Источник можно показать в настройках и citations; внутреннюю маршрутизацию выбирает общий dispatcher.

## Архитектурный контракт

Предлагаемые имена — новые, сейчас их нет в коде:

- `src/prm/nebula_connector.py`: типы `NebulaSelection`, normalized records и validation. Выбранные datasets, term/session, course/section refs, date window; не произвольный URL или Mongo query от LLM.
- `src/prm/runtime/nebula.py`: typed adapter поверх выбранного готового/сгенерированного клиента или существующего HTTP transport с injected test transport, resolver секрета и policy registry. Отдельный provider `provider_nebula`, capability `assistant.nebula_read`; собственный origin `https://api.utdnebula.com`, разрешённые path templates. Не маскировать под `provider_canvas` и не требовать Canvas institution grant.
- В `composition.py` — независимые секции Nebula/Canvas/mail и общий Academic coordinator. Его работа и сохранённые кандидаты не должны зависеть от наличия Canvas config. Natural dispatcher использует эту же службу.
- Выход — общий `SourceBatch` D10 с items, requested/checked coverage, truncation, failures, fetched_at. Он питает Search/Brief; только action-relevant записи становятся AcademicCandidate. Каталог курсов не превращать целиком в обязательства.
- Сохранять canonical `nebula:<dataset>:<record-id>`, raw source refs, URL первоисточника, term/session, field-path для конкретного срока, observed content hash и provenance. При отсутствии event ID — документированный стабильный ключ и отдельная неопределённость identity. Изменение времени не должно незаметно создавать второе событие.
- Date-only хранить как date с `date_precision`, timezone `America/Chicago` для UTD, исходным текстом и session; display timezone владельца отдельно. Не превращать дату в точный deadline 00:00/23:59. Existing точные Canvas даты сохранить обратно совместимо; ambiguous даты оставлять uncertain. DST и короткие учебные sessions входят в проверки.
- Source authority остаётся `aggregator`, пока конкретное утверждение не сверено с primary evidence. Недоступный PDF не выключает справочный ответ, но не позволяет сообщить подтверждённый срочный deadline. Чужие/общие даты не становятся личным обязательством без контекста.
- Минимум параметров уходит Nebula; профиль, переписка, email и рассуждения остаются локально. Присоединение публичного события к личному курсу/расписанию создаёт приватный derived context; egress к LLM оценивается по объединённому классу данных.
- Кэш — ограниченные выбранные записи в существующем хранилище, без зеркала всей MongoDB. Предложенные TTL для испытания: events 6 часов, catalog 24 часа, academic calendar 24 часа; не upstream SLA. Для срочного решения сверять первоисточник. Возраст и неизвестная upstream freshness видны пользователю.
- GET-only, редактирование ключа через существующий secret resolver, редактирование scope через общую настройку. Секрет не попадает в URL, citation, exception или trace. Не пересылать `x-api-key` по redirect/ссылкам на PDF. Таймаут, byte/page/call budget, cancel, 401/403→needs_access, 429→ограниченный backoff, schema drift→partial/unavailable. Пусто, stale и недоступно — разные состояния.
- Sync state хранить по dataset/selection/window: checkpoint, last_attempt, last_success, observed hash, coverage и next retry. Использовать общие durable jobs и storage, без второго scheduler. Concurrent sync одного selection не создаёт дубли; рестарт продолжает незавершённое окно. Исчезновение записи из неполного ответа не означает отмену события. ETag/Last-Modified применять только если конкретный endpoint действительно поддерживает их. Revoked scope прекращает чтение и использование кэша в соответствии с общей retention policy; ротация ключа не меняет record identity.

После каждого законченного implementation-пакета: **один Deep Review → исправления → следующий пакет**. Критические исправления перепроверяются адресно. D54 содержит provider evidence; не повторять весь NB-1/NB-2 и исторические PAI tiers из-за выдачи ключа. При обнаруженном несовпадении схемы исправить и проверить затронутый контракт.

Предлагаемые новые тесты (ещё не созданы): `tests/test_daily_nebula_connector.py`, `tests/test_daily_nebula_academic.py`, `tests/test_daily_nebula_brief_watch.py`. Регрессионный минимум выбирать по изменению из `tests/test_assistant_academic.py`, `tests/test_pai_academic_runtime.py`, `tests/test_external_watch_selection.py`, `tests/test_external_watch_fetch_safety.py`. Не запускать их сейчас для имитации готовности интеграции.

Первый шаг D54 — ограниченный canary: до 20 GET суммарно, один явный term, две выбранные даты и один выбранный курс/секция; повторить одну запись после согласованного интервала. Сохранить sanitized schema/coverage/latency/error receipt и несовпадения. Это начальная проверка доступа, **не конечный объём интеграции или приёмки**. Затем проверить все выбранные семейства endpoint и репрезентативные pagination/date/session случаи в пределах фактической quota. Нет оснований обещать полный каталог, current freshness или p95 по первым 20 запросам.

Приёмка D54: 14 дней, два недельных обзора и 20 заранее выбранных сценариев. Набор: 4 календарь/term/session; 4 курс/секция/преподаватель/сравнение; 4 события/клубы/предложения/место; 4 follow-up/сохранение/проект/возврат после рестарта; 4 Brief/Watch/изменение/остановка. Подтверждаемый календарный action дополнительно проверяется с D32; до его готовности фиксируется незакрытая зависимость полного Act-сценария. Длинный пилот совмещается с D38/D39, без второй обязанности владельца вести дневник.

Предлагаемые критерии, ещё не измеренные: не менее 16 из 20 задач дают полезный результат без существенной переделки; каждый обязательный выбранный dataset имеет успешный реальный read и честную coverage; ноль выдуманных точных дедлайнов, незаявленных пропусков окон, повторных уведомлений и неподтверждённых действий. Все срочные даты имеют primary support либо явно uncertain статус без ложного срочного обещания. Проверить scoped recovery после рестарта, 429, истечения доступа и изменения схемы; инъекции отказов пометить synthetic, не выдавать за реальные аварии провайдера. Скорость cold/warm запросов и стоимость измерить отдельно; SLO выбрать по замерам и приемлемому ожиданию владельца, не объявлять до проверки.

Для контроля точности сверить минимум 10 подходящих реальных записей с первоисточниками. На владельце — короткая оценка 3–5 ответов и двух Brief; остальные критерии проверяются по согласованным сценариям и безопасным trace. Обслуживание после стабилизации должно укладываться в общий ориентир ассистента 15 минут в неделю. Если Nebula дублирует Localist, сохранить полное выбранное покрытие через более надёжный источник и выключить лишний polling; качество ответа и способность наблюдать за темой сохраняются.

## Что запросить вместе с ключом

Владелец уже взял запрос ключа на себя; повторного решения о том, запрашивать ли его, не требуется. Предлагаемый текст для отправки самим владельцем:

> I’m building a private, single-user Telegram assistant for UTD academic planning and campus information. I’d like read-only access to academic calendars, campus events, course/section/professor records, clubs, discount programs, and room/location context where available. The assistant will query and cache selected data, link to official sources, and respect your quotas. Could you provision an API key and confirm production endpoint availability, quotas, update cadence, and any caching or attribution requirements? I don’t need database, upload, storage-write, or email-send access.

Особенно уточнить `/calendar/{date}` и `/academicCalendars/{id}`: наличие в develop не равно доступности за production gateway. Узнать допустимое хранение ключа на личном сервере и способ отзыва. Ключ передаётся в секретное хранилище при настройке; в задаче/чате/репозитории достаточно ссылки на credential, без значения. Уже записанный в старом access checklist путь — предложение, не доказательство наличия файла.

До ключа полностью исполнимы дизайн, код будущей интеграции, synthetic contracts, UX и Deep Review. Неизвестными остаются production schema, реальные quota/coverage/freshness и личная полезность. Они выделены в D54 и не задерживают общий план. «Полностью готово» допустимо после проверки согласованного пользовательского покрытия; отключённый обязательный dataset или незакрытый сценарий сохраняется открытым ограничением.
