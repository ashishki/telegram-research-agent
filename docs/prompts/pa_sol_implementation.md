# Sol — последовательная реализация Personal Assistant

Готовый стартовый промпт. Используется после выбора Sol владельцем в рабочей
сессии. Не задаёт API model ID/reasoning и не выдаёт live или release approval.

## Запуск всей локальной очереди

Скопировать блок в новую сессию Sol в этом репозитории:

```text
Выполни локальную часть плана docs/PA_IMPLEMENTATION_TASKS.md от PAI-00 до
PAI-26, последовательно по зависимостям. Начни с первой действительно
незавершённой готовой карточки. Это назначение локальной реализации полного
Personal Assistant, а не просьба ещё раз переписать план.

Прочитай AGENTS.md, актуальное начало docs/CODEX_PROMPT.md, правила и таблицу
порядка в docs/PA_IMPLEMENTATION_TASKS.md. Затем загрузи выбранную карточку,
её PA-Refs/контекст и действующие ASSISTANT_BOUNDARIES/IMPLEMENTATION_CONTRACT.
В PAI-01 прочитай полную PERSONAL_ASSISTANT_SPEC.md; дальше читай адресно.
Стратегия docs/PA_SCALING_STRATEGY_2026-10-06.md — обоснование, не runtime grant.

Проверь branch/HEAD/status, сохрани чужие изменения и untracked файлы.
Используй выбранную мной Sol текущей сессии без автоматического model override.
Работай непосредственно в назначенной ветке, не в master. Не начинай старые
PA-срезы заново по одному лишь статусу planned: сверяй существующий код и
evidence. PAI-номера теперь зарегистрированы как отдельный draft feature PAI в
docs/tasks.md и docs/design/PAI.design.json; PA-Refs сохраняют покрытие исходной
программы. Проверь регистрацию, planning/review gates и PAI-progress.

Разрешаю безопасную локальную реализацию назначенных карточек, изменения
необходимых файлов, synthetic fixtures, адресные тесты и изолированную
тестовую PostgreSQL PAI-02 без production DSN/данных/секретов. Эти полномочия
не заменяют формальное human design approval: подготовь конкретный reviewable
дизайн, используй pinned Playbook и не ставь approval поля вручную. Если
действующий workflow требует отсутствующего решения человека, покажи точный
готовый пакет и объясни gate; продолжай независимые разрешённые задачи.

Сначала переиспользуй и подключай существующие контракты. Каждая карточка
заканчивается заявленным наблюдаемым поведением: нужный путь проходит через
настоящие application/ingress/adapters, подменён только внешний I/O.
Не заканчивай на Protocol/DTO или skeleton. Новые tests/test_pai_*.py в плане
ещё не существуют: реализуй их и зарегистрируй проверки, не считай skip PASS.

Внутри карточки выполняй её acceptance и затронутые regression tests.
На границах фаз — требуемые tiers и независимые reviews по актуальной политике.
Не вызывай всех reviewers после каждого маленького patch. Не проверяй свою
работу как независимый reviewer. Устраняй P0/P1, затем получай независимый
recheck изменённого scope. Полный исторический pytest не запускай.

После каждой карточки обновляй docs/verification/PAI-progress.md, её receipt
и актуальную точку продолжения handoff: exact SHA/diff, changed files,
команды/results, evidence, unresolved gates, следующая карточка/команда.
Не называй local_verified человеческой или runtime приёмкой. Scoped Git
commit/push выполняй только при наличии действующих полномочий на публикацию;
не добавляй посторонние файлы или приватные данные.

После успешно закрытой карточки переходи к следующей готовой без вопроса
«продолжать?». Если независимая задача доступна, внешний blocker одного
аккаунта не останавливает всю работу. Не подменяй отсутствующее разрешение
истечением времени и не запрашивай заново уже выданный точный scope.

PAI-27…29 сначала подготовь до reviewable access/release/pilot пакетов.
Не подключай реальные аккаунты, не отправляй частные данные или сообщения,
не вызывай платные модели, не меняй production DB, не включай службы/таймеры
и не деплой без соответствующего отдельного scope. Не читай ключи ради
проверки наличия. Для Canvas нужен подтверждённый institutional access.
PAI-30/31 выполняй только после измеренного условия и оформления нужного ADR.

Не сокращай программу до MVP. Финальный outcome — Chat/Search/Brief/Watch/Act,
выбранные личные источники, память/media и реальная эксплуатация. Полное
завершение возможно только через PAI-29 / PA-18 и принятие владельцем.
До этого оставляй честный resumable checkpoint с готовыми частями и gates.
```

## Запуск одной карточки

```text
Выполни карточку PAI-07 из docs/PA_IMPLEMENTATION_TASKS.md по
docs/prompts/pa_sol_implementation.md. Объём этого поручения — только PAI-07
и необходимые локальные исправления её зависимостей. Сначала проверь их
evidence; завершённые зависимости не переписывай. После проверки сохрани
receipt и следующую команду. Live/production действия не разрешены.
```

Заменить `PAI-07` нужным ID. Это пример отдельного запуска, а не назначение
PAI-07 вместо первого прохода с PAI-00.

## Продолжение после паузы

```text
Продолжи реализацию по docs/prompts/pa_sol_implementation.md и
docs/PA_IMPLEMENTATION_TASKS.md. Прочитай docs/verification/PAI-progress.md
и актуальный handoff, сверяй их с текущим HEAD. Возобнови первую незавершённую
готовую карточку в ранее назначенном локальном scope. Не повторяй завершённые
задачи и несвязанные проверки. Все записанные live/design/release gates
сохраняются, пока нет конкретного решения владельца.
```

## Первая безопасная проверка

```bash
git status --short
git branch --show-current
git rev-parse HEAD
python3 tools/playbook.py --check-pin
python3 tools/check_personal_assistant_plan.py
```

При составлении пакета очередь начиналась с **PAI-00**. Актуальная точка
продолжения теперь — docs/verification/PAI-progress.md и current handoff.
